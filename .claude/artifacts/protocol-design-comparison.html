Two kernel-protocol designs for jupyter-dag, compared

The design in kernel-design-notes.md (sections 2 and 3, here the notes' design) against the simplification proposed the same day (here the simplified design). 2What the two designs share

Both put the same work in the frontend: topological order, cycle detection, staleness, conflict detection, a per-cell ledger of the names defined at the last run, gating on feature strings, and fallback analysis providers for kernels without the feature. Both reuse stop_on_error, silent, cellId, comms, and JEP 92 supported_features. Both defer value-carrying edges.

Both plan to prototype over a comm target in ipykernel. A comm target carries either design unchanged, so the footprint question decides what the pre-proposal says, not what can be built before October 19. Both also make the same mistakes, listed in section 6.

3Item by item

3.1 Scopes

notes' design

create_scope(parent), a scope field on execute_request, drop_scope. Run a shared prefix once, fork branches that rebind the same names. Child is a shallow dict copy or a lookup chain. Isolation holds "as long as cells rebind rather than mutate". Composes with subshells for concurrent branches. Pluto's workspace modules cited as the Julia version.

simplified design

No scopes. The reactive plugin enforces one definition per name; the DAG plugin enforces or flags the same rule from analysis. Under the rebind contract, branches with disjoint definitions in one namespace cannot interfere. Isolation for mutating code comes from a server-level clone.

What the review found

  • A lookup chain cannot be Python globals: exec() rejects a ChainMap. A bare dict copy assigned as user_ns breaks closures over cell-level names. A Python scope has to be a fresh module swapped into shell.user_module and shell.user_ns around each execute. Both reproduced in the venv.
  • Isolation is weaker than "rebind, don't mutate". Functions defined before the fork keep __globals__ bound to the parent dict, so a child's rebinding is invisible to upstream code and later parent rebinds leak in. Pluto avoids this only by re-running every dependent cell in the new module.
  • Scopes do not compose with subshells as written. InteractiveShell has one user_ns shared by every subshell thread; concurrent per-branch scopes need a context-local namespace inside IPython. %who, the debugger's variable views, and user_expressions would each need a scope parameter.
  • Pluto never forks workspaces. Each workspace#N replaces the last in a linear chain. Pluto is precedent for delete by module migration, not for branch isolation.
  • What the simplified design gives up: two branches that both end in model = fit(...); in-process parameter sweeps; and JavaScript's only route to "no hidden state", since a fresh context was the only way to make a let binding disappear.
  • The precedent I cited is narrower than I said. marimo, Pluto and Observable enforce one definer per name. No Hex document states such a rule, and Hex ships a fallback that runs cells in notebook order when it cannot infer dependencies.
  • Scopes never delivered isolation beyond the namespace level. RNG state, pd.set_option, the current matplotlib figure, os.chdir, and shared iterators leak through a shallow copy exactly as through one namespace.

VerdictThe cut is sound for the reactive plugin and for a proposal that has to land; scopes are the one item that would be reviewed the way subshells were, and they were unsound as written. It is a real loss for the DAG plugin, and it reduces to one product decision: may two branches of a user-drawn DAG define the same name?

3.2 Snapshots and clone

notes' design

snapshot_request and restore_request on shell, ordered with executions, plus list and delete. Manifest plus opaque blob; fidelity and uncaptured reporting. Tiers: replay, process-level CRIU via a provisioner ("kernel rebinds ZMQ ports"), language-native serialization. Clone preferred to restore for fan-out.

simplified design

Nothing in the kernel protocol. Replay needs nothing from the kernel; CRIU is a provisioner plus a Jupyter Server REST endpoint; the language-native tier is "the only one that needs kernel messages" and is Python-shaped. The DAG plugin codes against a server-level clone.

What the review found

  • Restore in place needs no protocol change, if the provisioner uses --tcp-close, keeps jupyter_client's restarter from replacing the kernel during the gap (it polls provisioner.poll() every 3 seconds), keeps the parent pid stable (ipykernel's parent poller exits within a second if it changes), and routes the restore through the existing restart path so JupyterLab clears futures and comms.
  • Clone by "restore one image twice" does not exist on a plain host. CRIU restores the original pid and bound ports; a second copy needs its own pid and network namespace, or kernel-side rebind code. ipykernel binds ports once at startup with no retry when a port is specified; the notes' "kernel rebinds ZMQ ports" describes a mechanism that does not exist. On a plain install the only clone is replay.
  • The language-native tier needs no messages either. Kishu implements checkpoint and checkout with IPython pre_run_cell and post_run_cell hooks plus silent execute_request with user_expressions. Messages buy a language-neutral, advertised contract with fidelity reporting; that is the notes' argument, and it is the right framing.
  • The Kishu figures hold verbatim: CRIU-Incremental up to 36 times slower on checkout for the largest notebook, comparable on checkpoint, faster on 3 of 8 notebooks, failed on 2 of 8.

VerdictRemoving the four message pairs from the kernel protocol is right and costs kernel authors nothing. The consequence for the DAG plugin is that the "isolation tier below" is replay in practice, a full prefix re-run per branch. That raises the price of dropping scopes without reversing it.

3.3 Delete

notes' design

A standalone namespace_request {delete: [names]} on the shell channel, before re-running a cell or when a cell is removed. No execution involved.

simplified design

An optional namespace_delete list on execute_request, applied before the code. Purge without running is an execute with empty code and silent. Advertised by a feature string; an unsupported list is silently ignored.

What the review found

  • Verified against ipykernel 7.3.0: empty code with silent: true does not increment the counter, publishes no execute_input, stores no history, still publishes busy and idle, still evaluates user_expressions, replies ok. Empty code without silent publishes an execute_input with a counter IPython never consumes, so the next cell repeats the prompt number. Silent is mandatory.
  • JupyterLab's CodeCell.execute refuses empty code; purges must call kernel.requestExecute directly.
  • No forced signature change: kernelbase already inspects do_execute for cell_meta and cell_id and passes them only where accepted. namespace_delete slots into the same list; bash_kernel's five-argument do_execute keeps working.
  • Failure differs. The field is silently ignored on a kernel without the feature (verified: x survived) and the cell runs against stale bindings with an ok reply. The notes' unknown message gets no reply at all, so the future hangs. A hang is an availability failure a timeout detects; a skipped delete is a correctness failure nothing detects. Under a gating bug the message fails safe and the field fails unsafe. The fix stays inside the field shape: advertise the string only when do_execute accepts the parameter, and echo removed names in the delta.
  • Abort. dispatch_shell aborts only execute_request after a stop_on_error failure, so a queued silent purge is aborted with the queue: right for rerun purges, wrong for cell-removed purges. A queued namespace_request is never aborted, which is the reverse.
  • The field fixes delete-before-run: a cell that fails has already lost its previous bindings, which is marimo's semantics. The message leaves the choice to the frontend.
  • On this axis the message is the reversible shape: a message can later gain a convenience field; a field cannot be retired without leaving two ways to do one thing.
  • Neither shape says what happens to names that cannot be removed: __builtins__, In, Out, JS let, R locked bindings, Julia consts. execute_reply has no slot for it.

VerdictThe field is the cheaper and tighter shape for the reactive plugin's common path, and delete-then-rerun becomes one atomic message. Its two costs are closable without a new message. Recommendation: the field, with the two mitigations and a not_deleted list on the reply.

3.4 Set one claim refuted

notes' design

namespace_request {set: {name: json}}: "a language-agnostic way to bind a name to a JSON-ish value", which is what widget-bound variables, papermill-style parameters, and DAG input ports all reduce to. Costs nothing extra. With user_expressions, emulates value-carrying edges.

simplified design

Dropped. JSON-to-binding is ambiguous in R, JavaScript and Julia, which is why papermill keeps per-language translators; comms already carry widget-bound values. It comes back only if value-carrying edges are chosen later.

What the review found

  • Refuted: "only needed if we later choose value-carrying edges". The notes listed three uses unrelated to value edges. Dropping set does not remove those needs; it moves them. An input cell or parameter on a kernel without a widget library becomes generated assignment source, papermill's translator layer living in the frontend, or does not exist.
  • What held: the ambiguity is real, and the two reactive notebooks that bind JSON values to names both shipped kernel-side conversion hooks for it (Pluto's transform_value, marimo's _convert_value).
  • papermill was the wrong witness. Its translators exist because it injects a source cell and needs each language's literal and assignment syntax; they hard-code one choice per language, do not resolve the numeric ambiguity, and there is no JavaScript translator at all.
  • "Comms already carry widget-bound values" is narrower than it sounds. Comms deliver a value to a trait on a kernel-side widget object, not to a name, and only on kernels with a widget library. Neither design covers Pluto's shape, a bound global name driven by a slider, without frontend bookkeeping from widget id to defining cell to name.
  • Real value-carrying edges need kernel-side handles for arbitrary objects; a JSON set emulates only JSON-representable values, so both designs overstate what set gives.

VerdictDropping set is a relocation, not a saving. It is still right for a first version whose thesis is reactive execution, because the spec burden of a per-language coercion table is real and the ambiguity undercuts the notes' "costs nothing extra" too. The decision is where the mapping lives, and it should be stated that way.

3.5 The runtime delta

notes' design

Optional namespace_delta: {added, rebound, removed} on execute_reply, from diffing global names and object identity before and after. "It works for languages with no parser support, and it's what ipyflow does inside ipykernel already."

simplified design

{added, removed} only, exact set differences, present whenever advertised. Rebound dropped: identity comparison either keeps old values alive or compares recycled ids, and static analysis already reports which names a cell assigns. Gives parser-less kernels such as bash the defines half of an edge for free.

What the review found

  • Added and removed are cheap (under 3 ms on a 100,000-name namespace). Both rebound problems are real and reproduced: x = None; x = [9,9,9] reports no rebind by id, and the pre-run copy keeps every replaced object alive until the reply.
  • "Exact" is exact only relative to a per-language enumeration the spec has to define. In ipykernel a raw key diff after one run reports _1, _i, _i1, _ii, _iii; the user_ns_hidden identity filter that %who uses is required. In R, library() changes the search path, not globalenv. In Julia, using is invisible before 1.12 and removed is always empty. In JavaScript, let and const are not properties of globalThis. In bash, PIPESTATUS, _, RANDOM, and SECONDS change on their own.
  • Subshells share one namespace, so a before-and-after diff attributes another subshell's assignments to this cell. The field must be present on status: error replies, since a failing cell can bind names before raising. Neither design says whether removed includes names removed by the same request's pre-run delete.
  • The dichotomy for rebound is not exhaustive: a weakref-where-possible hybrid bounds the memory cost, and instrumentation, which is what ipyflow actually does, detects rebinding exactly at CPU cost. Dropping rebound is a choice, not a necessity.
  • Dropping rebound blinds the two uses I gave the field. Cell A defines x; cell B runs exec("x = 2"); B's delta is empty because x already exists. On bash, count=$((count+1)) produces an empty delta after the first run, and bash_kernel needs two extra pexpect round trips per cell to get even first definitions.
  • The notes' "ipyflow proves it works" is wrong in the other direction: ipyflow traces with pyccolo; it does not diff namespaces.

VerdictThe shrink is defensible and additive; rebound can return as an optional key. The claims around it should be cut back: the field validates static analysis for new names only, and bash gets first definitions, not defines.

3.6 Where analysis runs

notes' design

Control channel, "like debug_request, which ipykernel services in a separate thread", because static analysis needs no namespace and should not queue behind a busy shell.

simplified design

Shell channel: same dispatch path as complete and inspect, no threading requirement on kernel authors, ordered with executions (a magic registered by an earlier cell changes how a later cell parses). Responsiveness during a long run from a subshell where the kernel has them.

What the review found

  • Norms. JEP 91 names completion, introspection, and variable inspection as things people put on control because it had its own thread, and says "this is considered bad practice as it should only be used for control purposes". Reviewers will quote it. The spec itself does not reserve control: it calls the channel "identical to Shell" on a separate socket, allows kernel_info there, and ipykernel accepts every shell message type on control. The notes' placement was against guidance, not against the spec.
  • Who is responsive today. A control thread exists in ipykernel and xeus-python. It does not in xeus-cpp or xeus-r, IRkernel, or in practice IJulia. Subshells exist in ipykernel 7 only; neither xeus nor xeus-zmq mentions them through their latest releases. On today's kernels the notes' route is responsive on a strict superset of kernels. The simplified design wins on direction and on what it asks of kernel authors, not on present capability.
  • Ordering. My IPython example was weak: %%foo and %foo rewrite textually whether or not the magic is registered; only single-line automagic and runtime-registered input transformers depend on live state. The requirement is real and strong elsewhere: Pluto expands macros in the live workspace module before resolving the topology, and a C++ cell cannot be parsed without the accumulated translation unit.
  • Ordering and responsiveness are mutually exclusive per request. A request sent to a subshell is ordered only within that subshell. The frontend picks per call, and the design should say so.
  • Thread safety does not discriminate. The single-line path enters builtin_trap, whose nesting counter is an unsynchronized read-modify-write shared with the executing thread. The hazard is identical for the control thread and a subshell thread, and ipykernel already runs transform_cell on subshell threads. The fix under either design is to call the static input_transformer_manager.transform_cell() and skip the prefilter.
  • An unknown message type on either channel gets no reply in ipykernel, and a message sent to a stale subshell_id is dropped with only a log line, so the frontend hangs rather than receiving the error JEP 91 promises.
  • Shell first is the reversible direction: shutdown_request's move from shell to control took a deprecation cycle, and JEP 80 shows a message can later be allowed on both channels.

VerdictShell, for the norms and the reversal path, with an explicit per-call policy and the honest statement that responsive analysis is ipykernel-only for now.

3.7 The shape of the analysis reply

notes' design

No schema. Per cell: defines, references, imports, confidence, has_unknown_references. Cell magics could declare their own inputs and outputs, as rpy2's %%R -i x -o y already says.

simplified design

analyze_request  {"code": ["df = pd.read_csv(path)", "df.head("]}
analyze_reply    {"status": "ok", "cells": [
  {"status": "ok", "defines": ["df"],
   "references": ["pd", "path"], "dynamic": false},
  {"status": "error", "ename": "SyntaxError", "evalue": "..."}]}

What the review found

  • code as a list conflicts with every other request, where code is a string. A spec maintainer would reject the reuse of the name with a different type.
  • Folding imports into defines is right for Python, JavaScript and C++ and wrong for R and Julia: library(dplyr) and using Foo bind nothing enumerable at top level yet must be ancestors of every cell that uses an exported name. Pluto keeps using as a separate class for this reason. A drawn-graph UI also wants to hide import edges. The notes' imports list was load-bearing.
  • One dynamic flag forces the frontend to treat "may define names I cannot see" and "may reference names I cannot see" identically; a star-import cell and an NSE-heavy R cell should schedule differently.
  • The per-cell error entry is the right shape; a syntax error must not fail the batch.
  • Neither design defines references: free variables only or all names read; whether reads inside function bodies count (marimo and Observable count them); whether obj.attr = 1 is a reference; whether x += 1 is both.
  • Both designs' "transform_cell then ast or symtable" undercounts the analyzer. transform_cell turns every cell-magic body into a string literal; %%capture out defines out; %%R -i x -o y needs per-magic argument parsing with no registry API to declare it; $var in ! and line magics expands at run time; symtable has no top-level-await flag; del x shows as an assignment. Measured cost is 2.5 ms per 200-line cell, so batching a notebook is fine.

3.8 Advertising and footprint

JEP 92 explicitly allows a feature to be "additional messages and/or additional fields in different existing messages", so gating fields on strings is conformant, and JupyterLab already parses the list. Three strings for one message and two fields is a worse ratio than JEP 91 or the debugger; a reviewer accepts it only if each string has a testable contract. Neither design names its strings or versions them, and JEP 91 itself says a version specifier is probably needed.

On cost, the review's strongest point: cost scales with the semantics kernel authors must implement, not with message count.

Scopes are in the JEP 91 class. analyze_request and namespace_delete are in the JEP 92 class. The simplified design's real saving is removing the one JEP 91 class item, not shaving message pairs.

6What both designs got wrong

  • "user_expressions already covers get." IRkernel returns an empty list, bash_kernel and metakernel return {}, xeus-cpp ignores the argument. Get exists on ipykernel, xeus-python, and IJulia.
  • Neither says what delete scrubs. A plain del user_ns[name] leaves the object reachable through Out[n], _, and _N.
  • Neither defines the delta's name set, its presence on error replies, its relation to the same request's delete, or its behavior under concurrent subshells.
  • Both treat stop_on_error as the partial-failure semantics a topological run needs. It aborts everything queued on the same subshell: over-aborting siblings when the scheduler pre-queues, doing nothing when cells go one at a time.
  • Both underestimate the analyzer and gesture at cell magics declaring their inputs and outputs without a mechanism.
  • Both misstate why snapshots would need messages: contract, not capability.
  • Both under-specify clone: "kernel rebinds ports" does not exist; "a REST change" hides the namespace requirement; neither mentions the restarter race or the parent poller.
  • Both misuse Pluto in opposite directions: as precedent for forkable scopes, which Pluto never had, and as "only for delete", when Pluto's delete is a module bump plus method deletion plus re-imports.
  • Both cite ipyflow for namespace diffing; it traces.
  • Both leave feature strings unnamed and unversioned, and both are silent on what a kernel that advertises delete does when a name cannot be removed.
  • Both assume analysis is order-free enough to run out of order somewhere. For IPython automagic, Julia macros, and C++ it is not.
  • Both describe set as the emulation route to value-carrying edges; real value edges need kernel-side handles for arbitrary objects.

7Gaps neither design covers

  • The ordinary execution path. Run Cell and Run All from the notebook view must go through the plugin or the ledger diverges from the kernel at once. JupyterLab 4 exposes a replaceable INotebookCellExecutor token and only one provider can hold it. Under the simplified design the replacement executor adds one field to the request it already sends; under the notes' design it sequences two futures.
  • Multiple clients on one kernel. A console, a second tab, or a collaborator runs x = 5 outside the ledger. Neither design has a kernel-side owner of "which cell defined this name". The ledger has to live in cell metadata in the shared model to be RTC-safe.
  • Ledger persistence. Reload, kernel restart, and opening a notebook whose kernel is still running all need a reconciliation story.
  • Temporaries under the one-definition rule. Ordinary notebooks reuse i, df, fig, ax, tmp across cells. marimo mangles underscore-prefixed names to cell-local names in the kernel; neither design has a way to express cell-private names. This will be the first complaint from any user of the reactive plugin.
  • The semantics of references and the policy for dynamic cells: run last, treat as defining everything downstream, refuse in reactive mode as marimo does for star imports, or warn. The value of dropping rebound depends on this policy.
  • Interrupt during a cascade. The scheduler must reconcile ran, aborted before run, and, under the notes' message shape only, deleted but never ran.
  • Which second kernel proves agnosticism. xeus-python drives an IPython InteractiveShell, so it shares the analyzer, the delete, the name filter, and the threading story with ipykernel. Deno, IRkernel, or IJulia each exercise a divergence the review found.
  • Effort accounting. The simplified design moves work to the frontend: per-language literal generation for parameters, conflict refusal or serialization, clone orchestration against an endpoint that does not exist. The notes' design moves work the other way: scope lifecycle, re-forking children when the prefix reruns, a scope id on every read.

8Decisions, with my recommendation

  1. May two branches of a user-drawn DAG define the same name? The whole scopes debate reduces to this, and it is about the DAG plugin, not the reactive one. Recommendation: no, for the first version. Enforce one definition per name, flag conflicts from analysis, offer clone-by-replay for real branching later. If yes, the notes' scopes come back with a fresh-module implementation and an IPython change for concurrency.
  2. Which plugin first. Reactive. Its surface is analysis, delete, and delta, and every shipped reactive notebook runs on that surface.
  3. Channel for analysis. Shell, with a stated per-call policy: main shell when ordering matters, a subshell when the kernel has them and the user is waiting.
  4. Delete as a field or a message. The field, with the delete string advertised only when do_execute accepts the parameter, removed names echoed in the delta, and a not_deleted list on the reply.
  5. Delete before run or on success. Before run, marimo's semantics, with the scheduler recording names undefined because the run failed.
  6. Rebound. Leave it out of the first version and reserve it as an optional key; state that the delta validates new names only.
  7. Set. Leave it out, and say that inputs are authored as code cells or ipywidgets in the first version, so the loss is named rather than hidden.
  8. Imports. Put the imports list back as an optional key carrying module names. It is load-bearing for R and Julia and cheap.
  9. One uncertainty flag or two. Two: unknown_defines and unknown_references.
  10. Feature strings. Three, named, each with a testable contract written before ipykernel ships them.
  11. The batch field. Do not reuse code for a list; use a differently named field.
  12. Build versus propose. Build the simplified surface over a comm target; let the pre-proposal name scopes and set as deferred with the reasons above, so the talk shows the small surface.
  13. Second kernel. IRkernel or Deno rather than xeus-python; either exercises a real divergence (no user_expressions and invisible library() in R; no delete for let in JavaScript).

9Conclusion

The simplified design is the one to propose, for a reason stronger than its message count: it removes the only item that would be reviewed like subshells, and that item was unsound as written. Its two irreversible commitments, shell channel and delete as a field, are the ones with the cheaper reversal paths or the closable failure modes. Every other cut is additive later.

The notes' design remains the more complete statement of what the DAG plugin was started for. Same-name branches, in-process sweeps, and language-agnostic input ports are real capabilities the simplified design gives up, and the "server tier below" I pointed at is replay on any plain install. That trade is a product decision, and it should be made explicitly rather than inherited from a protocol footprint argument.

Several of my stated reasons were wrong even where the conclusion stands, and they should not appear in a proposal: the Hex precedent, the IPython magic example for ordering, "no threading requirement", "for free" on bash, "only needed for value edges", the papermill attribution, copyToGlobals as session-free, and deletedCells as a kernel-side precedent.
